# Feature Specification: Export AGENTS.md Guidance and a Claude Skill from the Runefile with `rune export`

**Feature Branch**: `056-agent-docs-export`

**Created**: 2026-11-19

**Status**: Draft

**Input**: GitHub issue [#54](https://github.com/rune-task-runner/rune/issues/54)
(backlog ADOPT-3): "Export AGENTS.md and Claude skills from the Runefile". Related: client
setup (#53, spec 055), Rune-only agent mode (#46, spec 047), the value policy for agents
(#48, spec 050).

## Overview

An agent that reaches Rune through MCP is given the tasks as tools. An agent that has no MCP
integration has only its shell and the instruction files it reads, and somebody has to write
down for it which tasks exist and how each is called. That text is a second copy of the
Runefile and goes stale. This feature adds `rune export <format>`, which writes that text
from the Runefile.

```text
$ rune export agents-md
<!-- rune:begin tasks fingerprint=sha256:4be1...c07a -->
<!-- Generated by `rune export agents-md` from the Runefile. ... -->

## Rune tasks

This project's commands are tasks of its Runefile. Run a task with `rune <task>` ...
(the general text: how arguments are passed, what to do with a task that asks a person,
and that this text is guidance)

### `deploy`

Deploy the service.

- Usage: `rune deploy <env> [region]`
- Example: `rune deploy staging`
- `env`: required, one of `"staging"`, `"prod"`.
- `region`: optional, default `"eu-west-1"`.
- Asks a person to confirm: `"Deploy now?"`. Ask the person to run it.
- The author allows agents only `env` = `"staging"`.

<!-- rune:end tasks -->
```

The exact text of every line is in
[contracts/export-text.md](contracts/export-text.md), and the command's flags, reports and
exit statuses are in [contracts/rune-export.md](contracts/rune-export.md).

| Question | Today | After |
|---|---|---|
| How does an agent without MCP learn the tasks? | Somebody writes them into AGENTS.md by hand | `rune export agents-md` or `rune export claude-skill` |
| Is the text still right after the Runefile changed? | Nobody knows | `--check` says so and exits 1 when it is not. It writes nothing |
| Will the export damage the instructions I wrote? | A hand copy can | Only the marked section is Rune's. Every other byte of the file is kept |
| Does the export run my tasks to describe them? | Not applicable | Never. It reads the Runefile and runs nothing |
| Does the file stop an agent from running something? | Easy to assume | No, and the text says so. It is guidance |

Two formats:

| Format | What it is | Where `--write` puts it |
|---|---|---|
| `agents-md` | One Markdown section between two marker lines | `AGENTS.md` in the project |
| `claude-skill` | A skill directory: `SKILL.md`, and `tasks.md` when the catalog is large | `.claude/skills/rune-tasks/` in the project |

The project is the directory of the Runefile.

### Out of scope

- Generating or replacing this repository's own AGENTS.md or skills.
- Enforcing anything. The export states what the author declared. What enforces it is the
  MCP server (specs 031, 050, 053) and the client setup of spec 055.
- Other instruction formats: `CLAUDE.md` imports, Cursor rules, Copilot instruction files. A
  person can place the `agents-md` section in any Markdown file with `--output`.
- A user-wide or organization-wide location. The export writes where it is told, and its
  documented locations are inside the project.
- Describing task bodies, dependencies in full, or variables. The catalog is the callable
  surface: what a caller names and passes.
- A machine-readable catalog. `rune --dump --format json` already prints the parsed
  Runefile.
- Evaluating anything to make the text more precise: a default that is not a literal is shown
  as its expression, never as a value.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Print the tasks of a Runefile as guidance for an agent (Priority: P1)

A developer whose agent has no MCP integration runs `rune export agents-md` in a project with
a Runefile. The guidance is printed on standard output: a short text on how tasks are run,
and an entry for each public task with its description, its command line, its parameters and
what limits it.

**Why this priority**: this is the feature. Everything else decides where the text goes or
whether it is current.

**Independent Test**: Run the command against a fixture Runefile that has module tasks, typed,
defaulted and variadic parameters, tasks limited to an operating system, a private task and a
`[context]` task. Compare the output with the expected text, and run every printed example
through the command line's own argument handling.

**Acceptance Scenarios**:

1. **Given** a Runefile with public tasks, **When** the person runs `rune export agents-md`,
   **Then** standard output holds one entry per public task, in the order `rune --list`
   shows them, and nothing is written to any file.
2. **Given** a task with a description, a `[returns]` text and `[param-doc]` texts, **When**
   the export is printed, **Then** the entry holds the description, the returns text and each
   parameter's text.
3. **Given** a task `deploy env:enum("staging","prod") region="eu-west-1"`, **When** the export
   is printed, **Then** the entry shows the usage `rune deploy <env> [region]`, names `env` as
   required with its two values, and names `region` as optional with its default.
4. **Given** a task with a variadic parameter, **When** the export is printed, **Then** the
   usage marks it as repeatable and says whether at least one value is needed.
5. **Given** a task in a module `ops`, **When** the export is printed, **Then** the entry is
   named `ops::restart` and its usage is `rune ops::restart`.
6. **Given** a task marked `[linux]` and `[macos]`, **When** the export is printed on any
   operating system, **Then** the entry is there and says the task runs only on Linux and
   macOS.
7. **Given** a private task, a task whose name starts with `_`, and a `[context]` task,
   **When** the export is printed, **Then** none of them has an entry and none is named as
   something to run.
8. **Given** an enum value or an agent value with a space, a quote or a shell metacharacter,
   such as `us east`, `it's` or `a;b`, **When** the export shows it in an example command,
   **Then** a POSIX shell that reads the example passes exactly that value as one argument.
9. **Given** a default that is not a literal, such as `env("REGION", "eu-west-1")`, **When**
   the export is printed, **Then** the entry shows the expression in the Runefile's
   canonical form, says it is worked out when the task runs, and holds no value of the
   environment.
10. **Given** a task whose name is also a built-in command, such as `log`, **When** the export
    is printed, **Then** its usage is `rune -- log`.
11. **Given** a directory with no Runefile in it or above it, **When** the command runs,
    **Then** nothing is printed on standard output and the command exits 2 with the usual
    "no Runefile found" message.
12. **Given** a Runefile that does not pass analysis, **When** the command runs, **Then** the
    diagnostics are printed, standard output is empty and the command exits 3.
13. **Given** a Runefile whose tasks would create a marker file if any of them ran, including
    the `[context]` task, and with a default and a variable that call `error()` and so would
    stop the command if they were evaluated, **When** any export runs, **Then** it succeeds
    and no marker file exists afterwards.

### User Story 2 - Be told the limits of a task, and of the file itself (Priority: P1)

An agent reads the export before it runs a task. For a task that asks a person to confirm, a
task that applies a reviewed plan, and a task whose values the author limits for agents, the
entry says so and says what the agent does about it. The text never offers a way around the
limit, and it says plainly that the file enforces nothing.

**Why this priority**: a catalog that lists `deploy` without its limits invites the agent to
run it. A catalog that names the flag that skips the question teaches the workaround. Either
is worse than no export.

**Independent Test**: Export a fixture with `[confirm]`, `[agent-allow]`, `[plan]` and
`[applies]` tasks and a task that reaches a `[confirm]` task through a dependency. Read the
entries. Search every output for `--yes` and for a pipe into `rune`.

**Acceptance Scenarios**:

1. **Given** a `[confirm("Deploy now?")]` task, **When** the export is printed, **Then** the
   entry says the task asks a person to confirm, shows the question, and tells the agent to
   ask the person to run it.
2. **Given** a task `ship` that runs a `[confirm]` task `deploy` through a dependency or a
   hook, **When** the export is printed, **Then** the entry of `ship` says a run can reach
   `deploy`, which asks a person to confirm.
3. **Given** a task with `[agent-allow(env="staging")]`, **When** the export is printed,
   **Then** the entry says that the author allows agents only `env` = `staging`, and the
   example uses `staging`.
4. **Given** a task that reaches a task with `[agent-allow]`, **When** the export is printed,
   **Then** the entry names the reached task and its allowed values.
5. **Given** a `[plan]` task and the `[applies]` task of that plan, **When** the export is
   printed, **Then** the first entry says the task makes a plan that Rune stores, and the
   second says it applies that plan after a person approved it.
6. **Given** tasks marked `[readonly]` or `[network]`, **When** the export is printed,
   **Then** each entry states the declaration in the author's sense: declared read-only,
   declared to use the network.
7. **Given** any Runefile, **When** any export is produced, **Then** Rune's own text and
   every example do not contain `--yes`, do not show an answer piped into `rune`, and do not
   show a command that does a restricted task's work without Rune. An enum value `--yes`
   gives no example.
8. **Given** any Runefile, **When** any export is produced, **Then** the general text says
   that the file is guidance, that it does not limit what a shell can run, and that Rune
   enforces the confirmation and value limits only for calls through its MCP server.
9. **Given** any Runefile, **When** any export is produced, **Then** the general text says
   that arguments are positional values in the order shown and that `name=value` does not
   pass a parameter.

### User Story 3 - Put the guidance into AGENTS.md and keep what is already there (Priority: P1)

A developer runs `rune export agents-md --write`. A new `AGENTS.md` is created, or the
existing one gains Rune's section. Later the Runefile changes and the developer runs the
command again: only the section between Rune's two marker lines changes.

**Why this priority**: AGENTS.md is mostly hand-written. An export that a team cannot safely
run twice against that file will be pasted once and never refreshed, which is the problem
this feature removes.

**Independent Test**: Run with `--write` against fixtures: no file, a hand-written file with
no section, a file with a section in the middle, and files with broken markers. Compare every
byte outside the section, run again, and check that the second run writes nothing.

**Acceptance Scenarios**:

1. **Given** a project with no `AGENTS.md`, **When** the person runs
   `rune export agents-md --write`, **Then** `AGENTS.md` is created next to the Runefile and
   holds the marked section and nothing else.
2. **Given** an `AGENTS.md` with hand-written text and no marker lines, **When** the command
   runs with `--write`, **Then** the section is added at the end after one empty line and
   every byte that was there is unchanged.
3. **Given** an `AGENTS.md` with hand-written text before and after a marked section,
   **When** the Runefile gained a task and the command runs with `--write`, **Then** the text
   between the marker lines is the new section and every byte outside them is unchanged.
4. **Given** a file the command already wrote and an unchanged Runefile, **When** the command
   runs again, **Then** the file is reported as unchanged and is not written.
5. **Given** a file with two begin lines, a begin line with no end line, or an end line
   before its begin line, **When** the command runs with `--write`, **Then** nothing is
   written, the message names the file and the lines, and the command exits 2.
6. **Given** `--output docs/agents/tasks.md`, **When** the command runs, **Then** that file
   is created or updated by the same rules and `AGENTS.md` is not touched.
7. **Given** a file with Windows line endings, **When** the section is added or updated,
   **Then** the section's lines use them too.
8. **Given** a task description that holds a heading, a code fence, an HTML comment or the
   text of Rune's end line, **When** the section is written and then updated, **Then** the
   description is shown as text, the document has the same headings as before plus Rune's
   own, and the second update finds exactly one section.
9. **Given** the person runs the command in a subdirectory, **When** the Runefile is found
   in a parent directory, **Then** `--write` writes `AGENTS.md` in the Runefile's directory.
10. **Given** a write that succeeded, **When** the report is read, **Then** it names the
    file, says created, updated or unchanged, and gives the number of tasks and the size of
    the section.

### User Story 4 - Generate a Claude skill that lists the tasks (Priority: P2)

A developer who uses Claude Code runs `rune export claude-skill --write`. The project gains
the skill `rune-tasks` at `.claude/skills/rune-tasks/`. Its `SKILL.md` has valid frontmatter
with a description that says when to use it. For a Runefile with many tasks, `SKILL.md` stays
short and the entries are in `tasks.md` beside it.

**Why this priority**: a skill is loaded only when it is relevant, so it costs an agent less
than a section that is always read. It is the second format the issue asks for, and it
builds on the catalog of the first story.

**Independent Test**: Export a small fixture and a fixture with more tasks than the inline
limit. Parse the frontmatter of each `SKILL.md` as YAML, follow every link in it, and count
its lines.

**Acceptance Scenarios**:

1. **Given** a Runefile with a few tasks, **When** the person runs
   `rune export claude-skill --write`, **Then** `.claude/skills/rune-tasks/SKILL.md` exists,
   starts with frontmatter that parses as YAML and holds `name: rune-tasks` and a
   description, and holds the general text and every entry. No other file is written.
2. **Given** the same Runefile, **When** the entries of the skill and of the `agents-md`
   export are compared, **Then** they are the same entries in the same order, and both
   outputs carry the same fingerprint.
3. **Given** a Runefile with more tasks than the inline limit, **When** the skill is
   written, **Then** `SKILL.md` holds the general text, an index of at most the index limit
   with one line per task, and a link to `tasks.md`; `tasks.md` holds every entry; and the
   link resolves.
4. **Given** a Runefile with ten times the index limit, **When** the skill is written,
   **Then** `SKILL.md` is no longer than it is at the index limit plus one line that says how
   many more tasks `tasks.md` holds.
5. **Given** descriptions with a colon, a quotation mark, a `#`, `---` or a line break,
   **When** the skill is written, **Then** the frontmatter still parses and its values are
   single lines.
6. **Given** no `--write` and no `--output`, **When** the person runs
   `rune export claude-skill`, **Then** `SKILL.md` is printed on standard output; when the
   skill has a `tasks.md`, a note on standard error says that it is part of the skill and is
   written with `--write`.
7. **Given** a `SKILL.md` at the target that Rune did not generate, **When** the command
   runs with `--write`, **Then** nothing is written, the message names the file and how to
   proceed, and the command exits 2.
8. **Given** a skill Rune wrote with a `tasks.md`, **When** the Runefile shrank to a few
   tasks and the command runs with `--write`, **Then** `SKILL.md` holds every entry and the
   generated `tasks.md` is removed and reported as removed.
9. **Given** `--output .agents/skills/project-tasks`, **When** the command runs, **Then** the
   skill is written into that directory and its frontmatter name is `project-tasks`.
10. **Given** `--output` names a directory whose name is not a valid skill name, **When**
    the command runs, **Then** nothing is written and the usage error states the rule for
    the name.

### User Story 5 - Find stale guidance in CI (Priority: P2)

A maintainer adds `rune export agents-md --check` to CI. The step passes while the committed
section is what Rune would generate now, and fails after somebody changes a task without
regenerating. It never writes.

**Why this priority**: the check is what keeps the committed text true over time. The export
is useful without it, but drifts.

**Independent Test**: Write an export, run `--check` (exit 0), change a task's parameter, run
`--check` (exit 1, the reason named), and compare the directory before and after each check.

**Acceptance Scenarios**:

1. **Given** a file the command wrote and an unchanged Runefile, **When** the command runs
   with `--check`, **Then** it reports the file as current, writes nothing and exits 0.
2. **Given** a task that gained a parameter since the export, **When** the command runs with
   `--check`, **Then** it reports that the Runefile changed since the export, names the
   command that regenerates it, writes nothing and exits 1.
3. **Given** a section whose text was edited by hand while the Runefile is unchanged,
   **When** the command runs with `--check`, **Then** it reports that the section differs
   from what this Rune generates although the fingerprint matches, and exits 1.
4. **Given** no file at the target, or a file with no section, **When** the command runs
   with `--check`, **Then** it reports that the export is missing and exits 1.
5. **Given** a Runefile where only a task body, a private task or a comment that is not a
   description changed, **When** the command runs with `--check`, **Then** the file is
   current and the fingerprint is the same.
6. **Given** a current file whose line endings were changed from LF to CRLF by the checkout,
   **When** the command runs with `--check`, **Then** the file is current.
7. **Given** a skill with a `tasks.md` and a Runefile that no longer needs one, or the
   reverse, **When** the command runs with `--check`, **Then** it reports the export as stale
   and exits 1.
8. **Given** `--check` with `--write`, **When** the command runs, **Then** it is a usage
   error.
9. **Given** `--check --output path`, **When** the command runs, **Then** that path is
   checked in place of the documented location.

---

### Edge Cases

- The Runefile has no public task: the export is still produced. It holds the general text
  and says that the Runefile has no public tasks. `--check` works on it as on any other.
- The Runefile has a task named `export`: `rune export` is the command. It prints a note on
  standard error that the task is run with `rune -- export`. `rune export` followed by
  anything that is not a format is a usage error that names `rune -- export`, so it never
  succeeds without doing what was asked. In the catalog that task's usage is
  `rune -- export`.
- No format, or an unknown one: a usage error that lists the two formats.
- A description of several lines: it is shown as one paragraph. A description longer than
  the limit for agent-facing text is cut at that limit and marked as cut.
- A description, a returns text, a parameter text, a confirm question or a value that holds
  Markdown or HTML: it is shown as text. It cannot start a heading, a list, a code block, a
  comment or a marker line, and cannot end one.
- A value that holds a backtick, a `$` or a control character such as a line break: where it
  is listed as a value it is written with an escape, so no such character from the Runefile
  is in the output, and it is never used in an example. Instruction files give these
  characters a meaning of their own: Claude Code runs a command written between backticks
  after `!` when it loads a skill, and replaces `$` placeholders.
- A description that holds `@path`: the `@` is written so that a client that imports files
  named that way in an instruction file does not import one.
- An example value that is empty: it is written as `''`.
- An example value that holds a single quote, a double quote, a backslash, a space, `;`,
  `&`, `|`, `*` or `#`: the example still passes exactly that value as one argument to a
  POSIX shell.
- A required parameter with no value Rune can know, such as a free string or a number: the
  entry has the usage and no example. No value is invented.
- A parameter default that names a variable or calls a function: the expression is shown as
  the Runefile has it. Nothing is evaluated, no file is read, no environment variable is
  read.
- A Runefile that loads a dotenv file or exports variables: the export is the same whatever
  the environment and the dotenv file hold.
- The same Runefile exported on Linux, macOS and Windows: the bytes are the same, apart from
  line endings taken from an existing file.
- The target file starts with a UTF-8 byte order mark, or does not end with a line break: the
  mark is kept, and the section still starts on its own line. A file that holds only the
  mark gets the section after it, and the next run finds that section.
- A marker line that appears inside hand-written text more than once, for example in a
  quoted example: the file is ambiguous and is refused with the lines named. The person
  changes the quoted text.
- The target of `--write` is reached through a symbolic link that leads outside the project:
  nothing is written through it, and the message names the path and where it leads. A path
  given with `--output` is written as given.
- `--output` names a directory for `agents-md`, or an existing file for `claude-skill`: a
  usage error.
- `--write` together with `--output`: the path of `--output` is used.
- The target cannot be read or written: no file of the export is left half-written, and the
  message names the file. Exit 1.
- A `tasks.md` in the skill directory that Rune did not generate: it is never replaced or
  removed. When the catalog needs a `tasks.md`, the export is refused as for `SKILL.md`.
- A committed export that an older or newer Rune generated with other wording: `--check`
  reports it as different with a matching fingerprint. The documentation says to regenerate
  after an upgrade.
- A task that is limited to one operating system and reaches a `[confirm]` task: the reach is
  stated whatever the host, because the text must not depend on where it was generated.

## Requirements *(mandatory)*

### Functional Requirements

**The command**

- **FR-001**: Rune MUST provide `rune export <format>`, where the format is `agents-md` or
  `claude-skill`. Any other name, or none, MUST be a usage error that lists the two.
- **FR-002**: The command MUST find the Runefile as other commands do: from the working
  directory upward, or the one named with `--file`. The directory of that Runefile is the
  project.
- **FR-003**: The command MUST stop before producing anything when no Runefile is found
  (exit 2) or the Runefile does not pass analysis (exit 3, with the diagnostics).
- **FR-004**: The command MUST NOT run a task, a hook, a `[context]` task or a task body,
  MUST NOT evaluate a default, a variable, a setting or any other expression, MUST NOT read
  the environment's variables or a dotenv file for content, MUST NOT start a program, and
  MUST NOT use the network. It reads the Runefile and the files that Runefile imports, and,
  when it writes or checks, the target files.
- **FR-005**: When the Runefile defines a task named `export`, the command MUST print a note
  on standard error that the task is run with `rune -- export`. `rune export` with anything
  but exactly one format MUST be a usage error that names `rune -- export`.
- **FR-006**: With neither `--write` nor `--output` nor `--check`, the command MUST print
  the export on standard output and MUST NOT create or change any file. For `claude-skill`
  standard output holds `SKILL.md` only.

**The catalog**

- **FR-007**: Both formats MUST be produced from one catalog of the Runefile's public tasks,
  so that they state the same tasks, the same order, the same command lines and the same
  limits.
- **FR-008**: The catalog MUST hold every task that is not private and is not the
  `[context]` hook, including tasks of modules and tasks limited to an operating system
  other than the host's. A private task and the `[context]` hook MUST NOT have an entry.
  Private is what it is for `rune --list` and for the MCP server: the `[private]` attribute,
  or a full name that starts with `_`. The export uses that one rule and adds none.
- **FR-009**: The order of the entries MUST be the order of `rune --list` on a host that
  can run every task, without the `[context]` hook: by group in the order each group first
  appears, and by declaration inside a group. The catalog MUST NOT
  depend on the host's operating system, the working directory, the environment, the time
  or the Rune version's build.
- **FR-010**: Each entry MUST hold: the task's full name, with its module prefix where it
  has one; its description; its usage; each parameter; its group when it has one; the
  operating systems it is limited to; its returns text when it has one; and the limits of
  FR-016 to FR-020.
- **FR-011**: A description, a returns text and a parameter text MUST each be shown as one
  paragraph of plain text, cut at the limit Rune uses for agent-facing text, with the cut
  marked.

**Command lines**

- **FR-012**: The usage of a task MUST be `rune`, the task's name and its parameters in
  declaration order, marked as required, optional, one or more, or zero or more. It MUST
  show positional values only. It MUST NOT show a parameter as `name=value`, as a flag or
  as JSON.
- **FR-013**: The usage of a task whose name is a built-in command of Rune MUST start with
  `rune --`.
- **FR-014**: An entry MUST show one example command when the task has a parameter that
  needs a value and Rune knows a value for each one without evaluating anything. A parameter
  needs a value when it is required, or when the author allows agents a value for it and
  its default is not the literal equal to that value (a default that is computed counts as
  not equal). The value is the one the author allows agents, else the literal default of an
  optional parameter, else the first value of an enum, else `true` for a boolean, so that an
  example never sets an option the caller could have left alone. The example holds the
  parameters up to the last one that needs a value, and no variadic values beyond the one a
  one-or-more parameter needs. An entry MUST NOT show an example with an invented value, and
  MUST NOT show one when a value it would hold has a backtick, a `$`, `<`, `>` or a
  character that is not printable, or starts with `-`.
- **FR-015**: Every value in an example MUST be written so that a POSIX shell passes it to
  Rune as exactly one argument with exactly its bytes, whatever spaces, quotes, backslashes
  or other shell metacharacters it holds. Every example, given to
  Rune's own command-line handling, MUST name the task and bind the values the example was
  built from.

**Parameters**

- **FR-016**: For each parameter the entry MUST state: its name; whether it is required;
  whether it takes several values; its declared type when it has one; the allowed values of
  an enum; its default; and its `[param-doc]` text. A literal default is shown as its value.
  Any other default is shown as the expression the Runefile holds, in canonical form, with
  the statement that it is worked out when the task runs.

**Limits**

- **FR-017**: For a `[confirm]` task the entry MUST say that the task asks a person to
  confirm, show the author's question when there is one, and tell the agent to ask the
  person to run the task. For a task that can reach `[confirm]` tasks through dependencies
  and hooks, the entry MUST name them.
- **FR-018**: For a task with `[agent-allow]` the entry MUST state each parameter and the
  one value the author allows agents. For a task that can reach tasks with `[agent-allow]`,
  the entry MUST name them with their allowed values. The entry MUST NOT claim that a run
  from a shell is refused.
- **FR-019**: For a `[plan]` task the entry MUST say that the task makes a plan that Rune
  stores. For an `[applies]` task the entry MUST name the plan task and say that the plan is
  applied only after a person approved it.
- **FR-020**: For `[readonly]` and `[network]` the entry MUST state the author's declaration
  and present it as a declaration.
- **FR-021**: The text Rune generates, and every example, MUST NOT contain `--yes`, an
  answer piped or redirected into `rune`, a setting or flag that grants or skips an
  approval, or a command that does a limited task's work without Rune. A value from the
  Runefile that starts with `-` is never put into an example, so no example can pass a flag.
  What the author wrote in a description is shown as text, as the author wrote it.
- **FR-022**: The general text of every export MUST say: that the tasks are run with
  `rune <task>`; that arguments are positional values in the order shown, quoted for the
  shell, and that `name=value` does not pass a parameter; what an agent does with a task
  that asks a person to confirm or applies a plan; that the values the author allows agents
  are to be used as stated; that the text is guidance and does not limit what a shell can
  run; and that Rune enforces these limits only for calls through its MCP server.
- **FR-023**: The words "restricted", "locked down", "safe", "secure" and "sandboxed" MUST
  NOT describe what the exported file does.

**Text safety**

- **FR-024**: Text taken from the Runefile MUST NOT be able to change the structure of the
  output: it cannot open or close a heading, a list, a block quote, a table, a code block,
  a code span, an HTML element or comment, a link, a frontmatter block or one of Rune's
  marker lines. Every such text is shown to a reader as the characters the author wrote.
- **FR-024a**: Text taken from the Runefile MUST NOT be able to make a client act when it
  loads the file. No backtick, no `$`, no `<` and no `>` in the output comes from the
  Runefile, so that no
  such text is run as a command or replaced as a placeholder when a skill is loaded, and no
  `@` from a description stands where a client would read it as a file to import.
- **FR-025**: The frontmatter of a generated `SKILL.md` MUST parse as YAML into string
  values on single lines, whatever the Runefile holds.

**Writing**

- **FR-026**: `--write` MUST write the export to its documented location in the project:
  `AGENTS.md` for `agents-md`, and the directory `.claude/skills/rune-tasks/` for
  `claude-skill`. `--output <path>` MUST write to that path in its place: a file for
  `agents-md`, a skill directory for `claude-skill`.
- **FR-027**: In a Markdown file, Rune owns exactly the lines from its begin line to its end
  line. The begin line MUST carry the fingerprint and MUST be recognizable as Rune's.
- **FR-028**: Writing `agents-md` to a file that does not exist MUST create it with the
  section alone. Writing to a file with no marker line MUST add the section at the end.
  Writing to a file with exactly one begin line followed by exactly one end line MUST
  replace the lines from the one to the other.
- **FR-029**: In an existing file every byte outside Rune's section MUST be unchanged, and
  the section's line endings MUST be the file's.
- **FR-030**: A file whose marker lines are not exactly one begin line followed by one end
  line, and not absent, MUST be refused: nothing is written, the message names the file and
  the line of each marker, and the command exits 2. No flag overrides this.
- **FR-031**: A skill file is Rune's as a whole and MUST carry a generated line: a line
  that says Rune generated the file, with the fingerprint. A `SKILL.md` or `tasks.md` at the
  target that the catalog needs and that does not carry a generated line MUST NOT be
  replaced, and no file without a generated line is ever removed: nothing is written, the message names the file, and the
  command exits 2.
- **FR-032**: A skill MUST be `SKILL.md` alone when the catalog has at most the inline limit
  of tasks. Above it, `SKILL.md` MUST hold the general text, an index of one line per task
  for at most the index limit of tasks, the number of tasks not in the index, and a link to
  `tasks.md`, and `tasks.md` MUST hold every entry. Both limits are fixed and documented.
- **FR-033**: When a skill no longer needs its `tasks.md`, writing MUST remove a `tasks.md`
  that Rune generated, and report it.
- **FR-034**: The frontmatter name of a skill MUST be the name of its directory: `rune-tasks`
  on standard output and with `--write`. With `--output` the directory's name MUST be a
  valid skill name, or the command is a usage error that states the rule.
- **FR-035**: The description in the frontmatter MUST say what the skill holds and when to
  use it, and MUST stay within the length a skill description may have, whatever the number
  of tasks.
- **FR-036**: All targets of one run MUST be checked before the first is written. When a
  file cannot be written, the files the run already wrote MUST be put back as they were, and
  the file that failed MUST be named.
- **FR-037**: A run that would change nothing MUST write nothing and report each file as
  unchanged.
- **FR-038**: When the target is the documented location, a target that a symbolic link
  takes outside the project MUST be refused with the path named. A path given with
  `--output` is the person's choice and is used as given.
- **FR-039**: A run that writes MUST report on standard error, for each file: its path,
  whether it was created, updated, removed or left unchanged, and, for a file created or
  updated, the number of tasks and the size of what Rune wrote.

**Determinism, fingerprint and check**

- **FR-040**: For an unchanged Runefile and the same Rune version, the export MUST be the
  same bytes on every run, in every directory, on every operating system and under every
  environment.
- **FR-041**: Every export MUST carry a fingerprint computed from the catalog: every fact an
  entry states, and nothing else. A change to something the export states MUST change it. A
  change to a task body, to a private task that no public task reaches, or to a comment that
  is not a description MUST NOT change it. Both formats of one Runefile carry the same
  fingerprint.
- **FR-042**: `--check` MUST compare the target with what the command would write now. It
  MUST write nothing. It MUST exit 0 when they are the same and 1 when not, apart from the
  refusal of FR-044. A difference
  only in line endings is not a difference.
- **FR-043**: When the target differs, `--check` MUST say why in one of these terms: the
  export is missing; the Runefile changed since the export (the fingerprints differ); or the
  text differs although the fingerprint matches, which means it was edited or was generated
  by another Rune version. It MUST name the command that regenerates the export.
- **FR-044**: `--check` MUST check the documented location, or the path of `--output`.
  `--check` with `--write` MUST be a usage error. For a skill it MUST check `SKILL.md`,
  `tasks.md`, and that no generated `tasks.md` is left where none belongs. A target that a
  write would refuse (FR-030, FR-031, FR-038) MUST be reported by `--check` as the write
  reports it, with exit 2: its state cannot be compared.
- **FR-045**: The exit status MUST be 0 when the export was printed, written or found
  current; 1 when `--check` found it missing or different, or a file could not be read or
  written; 2 for a usage error, no Runefile, or a target the command refuses to change; 3
  for a Runefile that is not valid.

**Documentation**

- **FR-046**: The documentation MUST describe the command, each format and each flag, the
  documented locations, the marker lines and what Rune owns, how to regenerate, how to use
  `--check` in CI, and how to remove an export.
- **FR-047**: The documentation MUST say how each output reaches an agent: which clients
  read `AGENTS.md` and from where, where a Claude skill is found and when it is loaded, and
  how to place the section in another instruction file.
- **FR-048**: The documentation MUST distinguish guidance from enforcement: the export
  states the author's limits and enforces none; an agent with a shell can run any command;
  what enforces the limits is the MCP server, and what removes the shell is the setup of
  `rune agent init`.
- **FR-049**: The documentation MUST state that a task named `export` is run with
  `rune -- export`, and the release notes MUST call that change out.

### Key Entities

- **Catalog**: the public tasks of one Runefile in listing order, with the facts the export
  states about each. Both formats are rendered from it, and the fingerprint is computed from
  it.
- **Entry**: one task of the catalog: name, description, usage, example, parameters, group,
  operating systems, returns text and limits.
- **Limit**: something the author declared that an agent has to respect: a confirmation, a
  value allowed for agents, a plan to apply, with the tasks a run can reach that carry one.
- **Fingerprint**: a digest of the catalog. It says which state of the Runefile's callable
  surface an export describes.
- **Owned content**: what Rune may replace: the lines between its two marker lines in a
  Markdown file, and a skill file that carries Rune's line.
- **Target**: where an export is written or checked: a Markdown file, or a skill directory.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For every fixture Runefile, 100% of the public tasks have an entry in both
  formats, and 0 private or `[context]` tasks do.
- **SC-002**: 100% of the examples in every fixture export are accepted by Rune's own
  command-line handling and bind exactly the values they were built from, including values
  with spaces, quotes, backslashes and `;`. Every usage names its task as the command line
  takes it and lists that task's parameters in their order.
- **SC-003**: After any export against a fixture whose every task and hook would leave a
  trace, and whose defaults, variables and settings would fail if they were evaluated, the
  export succeeds and no trace exists, and no value of the environment or of a dotenv file
  appears in any output.
- **SC-004**: In every write fixture, 100% of the bytes outside Rune's section are identical
  before and after, and a second run with an unchanged Runefile writes nothing.
- **SC-005**: Two exports of the same Runefile are byte-identical across runs, working
  directories and the three operating systems of CI.
- **SC-006**: `--check` exits 1 for every fixture change that alters what an entry states
  and 0 for every change that does not, and the project directory is identical before and
  after every check.
- **SC-007**: Every generated `SKILL.md` has frontmatter that a YAML parser reads into the
  expected name and description, and every link in it resolves to a generated file.
- **SC-008**: `SKILL.md` for a Runefile with ten times the index limit of tasks is at most
  one line longer than for a Runefile at the index limit.
- **SC-009**: In no fixture export does Rune's own text or an example contain `--yes`, and
  every fixture export contains the statement that the file is guidance and enforces
  nothing.
- **SC-010**: A person can go from a Runefile to a committed `AGENTS.md` section with a CI
  check by following only the documentation page, in under five minutes.

## Assumptions

- The command is named `rune export`, as the issue writes it. It takes the name `export` on
  the command line, as `log`, `import` and `agent` took theirs. A task named `export` stays
  a task and an MCP tool, and is run with `rune -- export`. This is a breaking change for a
  Runefile with such a task and is called out in the release notes.
- The default is standard output, as the issue asks. `--write` is the explicit request to
  write to the documented location, and `--output` names another one. There is no `--force`:
  the two refusals (ambiguous markers, a file Rune did not generate) are resolved by the
  person in the file, which keeps the command from ever replacing hand-written text.
- A file with no marker line gains the section at its end. That is an addition, not an
  overwrite: every existing byte is kept.
- The skill is named `rune-tasks` and lives at `.claude/skills/rune-tasks/`, the project
  location Claude Code reads skills from. The exact frontmatter fields and limits follow the
  client's documentation as read during planning.
- The inline limit is 30 tasks and the index limit is 100 tasks. They are constants, not
  flags. Planning may adjust the numbers; the behavior of FR-032 stays.
- The `agents-md` section has no size limit of its own. The report gives its size, and the
  documentation names the limits clients put on instruction files and points to the skill
  format for large catalogs.
- Examples are written for a POSIX shell (`sh`, `bash`, `zsh`), which is what agent clients
  run commands in on Linux and macOS, and the text says so. The same example is printed on
  every operating system so that the export is byte-stable.
- The export lists a task that is limited to another operating system, with the limit
  stated, because a committed file is read on machines other than the one that generated it.
  `rune --list` hides such a task on a host it cannot run on; the export cannot depend on
  the host.
- A reach is stated when any path of dependencies and hooks leads to the task, without
  regard to the host's operating system. This can name a task that a run on one host would
  skip. It never hides one.
- The fingerprint covers the catalog and not the source bytes, so that a commit that changes
  only task bodies does not make a committed export stale.
- The fingerprint does not cover the Rune version. A new Rune version that words an entry
  differently makes `--check` fail with the reason of FR-043, and the fix is to regenerate.
- The export says nothing about the MCP server's operator settings (`--allow`,
  `--allow-destructive`, `--deny`, `--sandbox`), which are not in the Runefile.
- The report is text for a person. A script uses the exit status.
